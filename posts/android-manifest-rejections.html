“Manifest merger failed with multiple errors” — read the report, fix the conflict

You changed one line, hit build, and got this:

Execution failed for task ':app:processReleaseManifest'.
> Manifest merger failed with multiple errors, see logs

That sentence is not an error message. It is a summary: the merger found more than one conflict and printed one line instead of several. Everything you need is in the report it wrote, and the report is the part nobody reads.

This post is the reading order — where the report is, the four conflicts it names most often, the exact attribute that fixes each one, and why the same error keeps coming back in Expo projects after a clean build.

Find the merger report

Gradle writes a plain-text report next to the build outputs. For a release build it is:

android/app/build/outputs/logs/manifest-merger-release-report.txt

With flavours or build types the filename follows the variant: manifest-merger-internalRelease-report.txt and so on. The merged result itself — the file that actually ships — is here:

android/app/build/intermediates/merged_manifests/release/AndroidManifest.xml

If the report is missing or you only have the one-line summary, rerun the manifest task alone with the stack trace on. It finishes in seconds and stops before anything else in the build can bury the message:

cd android
./gradlew :app:processReleaseManifest --stacktrace

Search the output for ERROR and read the blocks under it. Each block names the attribute, both values, and the two files that disagree. That is your whole diagnosis.

Conflict 1: the same attribute with two different values

By far the most common shape. Two manifests declare one attribute — usually on <application> — with different values, and the merger refuses to guess:

Manifest merger failed : Attribute application@theme value=(@style/AppTheme) from AndroidManifest.xml:12:9-45
    is also present at [com.some.sdk:1.4.0] AndroidManifest.xml:9:18-63 value=(@style/SdkTheme).
    Suggestion: add 'tools:replace="android:theme"' to <application> element at AndroidManifest.xml:11:3-45 to override.

The merger even tells you the fix, which is why this one is embarrassing rather than hard. Declare the tools namespace on the root element and override the specific attribute — not the whole element:

<manifest xmlns:android="http://schemas.android.com/apk/res/android"
          xmlns:tools="http://schemas.android.com/tools">

  <application
      android:theme="@style/AppTheme"
      tools:replace="android:theme">

List only the attributes you are actually overriding. A blunt tools:replace="android:theme,android:icon,android:label,android:allowBackup" is how a library’s deliberate value gets silently dropped and a later bug gets blamed on the library.

The same message appears for android:name on a merged component — two providers claiming the same authority, for instance. tools:replace works there too, but stop and check whether both providers are genuinely needed first; overriding an authority collision can leave a content provider unreachable at runtime.

Conflict 2: minSdk lower than a library’s

Manifest merger failed : uses-sdk:minSdkVersion 21 cannot be smaller than version 24 declared in library [com.example:lib:2.1.0]

A dependency requires a newer Android version than your app declares. You have two honest options and one dishonest one.

Raise minSdk — usually correct. In Expo that is one plugin entry, not a hand-edited Gradle file:

{
  "expo": {
    "plugins": [
      ["expo-build-properties", { "android": { "minSdkVersion": 24 } }]
    ]
  }
}

Drop the library if it is pulling in a much newer floor than the feature is worth. Check ./gradlew :app:dependencies for who brought it in — it is often a transitive dependency of something else, and a patch-level bump of the parent can fix the floor without you touching minSdk at all.

The dishonest option is tools:overrideLibrary, which tells the merger to ignore the requirement:

<uses-sdk tools:overrideLibrary="com.example.lib" />

It compiles, and then the library calls an API that does not exist on API 21 devices and you get a NoSuchMethodError in production instead of a build failure. Treat it as a last resort, and only when you know the newer code path is never reached.

Conflict 3: a component with an intent filter and no android:exported

Since Android 12, any activity, service or receiver with an <intent-filter> must state android:exported explicitly. AGP surfaces the omission as a merge error rather than a quiet default:

Manifest merger failed : android:exported needs to be explicitly specified for element
    <activity#com.example.MainActivity>. Apps targeting Android 12 and higher are required to
    specify an explicit value for android:exported when the corresponding component has an intent filter.

The value is a security decision, not a formality:

  • Launcher activity → android:exported="true". Nothing else works.
  • Your own deep-link scheme (myapp://) → usually false. Another app cannot open it, and nothing legitimate needs to.
  • App Links on your own https domain → true, plus autoVerify="true" and the asset-links file on the server.
  • SDK components → the library should declare it. If it does not, that is a library bug; overriding it in your manifest with tools:node="merge" is a workaround worth commenting in the repo.

If the offending component comes from a library, add the attribute without taking ownership of the element:

<activity
    android:name="com.some.sdk.RedirectActivity"
    android:exported="false"
    tools:node="merge" />

Conflict 4: tools:replace with nothing to replace it with

A confusing one, because the error blames the fix you just added:

Manifest merger failed : tools:replace specified at line:14 for attribute android:label,
    but no new value specified

You asked the merger to override an attribute without giving it the value to use. tools:replace is an instruction, not a value — the attribute has to be present on the same element:

<application android:label="@string/app_name" tools:replace="android:label">

The inverse also bites: tools:replace written on <manifest> instead of <application> does nothing, because the merge happens per element.

Why it comes back after a clean build in Expo

This is the part that wastes an afternoon. You fix the manifest, build passes, you run npx expo prebuild --clean or delete android/, and the identical error returns.

Because android/app/src/main/AndroidManifest.xml is generated whenever the native project is regenerated — it is output, not source. A hand edit survives exactly until the next prebuild.

Put the change where the generator will read it:

  • Simple values — app.json: android.permissions, android.blockedPermissions, and the expo-build-properties plugin for SDK levels.
  • Anything structural — a config plugin using withAndroidManifest. It runs during prebuild, so the edit is reproducible and survives --clean:
// plugins/withExportedFlag.js
const { withAndroidManifest } = require('expo/config-plugins');

module.exports = function withExportedFlag(config) {
  return withAndroidManifest(config, (cfg) => {
    const app = cfg.modResults.manifest.application?.[0];
    const activities = app?.activity ?? [];
    const launcher = activities.find((a) =>
      a['intent-filter']?.some((f) =>
        f.action?.some((x) => x.$['android:name'] === 'android.intent.action.MAIN')));
    if (launcher) launcher.$['android:exported'] = 'true';
    return cfg;
  });
};

Rules of thumb: never edit android/ without expecting to lose it, and treat a merge error that reappears after prebuild as proof the fix was in the wrong layer.

Once the merge succeeds: the attributes that get you rejected later

A green build is not a green submission. These are the manifest values that pass the merger and then fail Play review, install, or the Data safety audit.

android:debuggable="true" in a release

Usually a hand-run assembleDebug or a stale debug applicationId in the merged manifest. The merged file is the only one worth checking, because it is the one packaged.

usesCleartextTraffic="true"

A blanket allowance means the app may speak HTTP, which contradicts the “data encrypted in transit” answer in the Data safety form. If one dev host genuinely needs it, scope it instead:

<application android:networkSecurityConfig="@xml/network_security_config">
<!-- res/xml/network_security_config.xml -->
<network-security-config>
  <domain-config cleartextTrafficPermitted="true">
    <domain includeSubdomains="false">10.0.2.2</domain>
  </domain-config>
</network-security-config>

allowBackup="true"

Not a rejection by itself, but it lets anyone with adb extract app data from a signed build — awkward to explain in a privacy review. For apps holding credentials or health data, android:allowBackup="false" is the defensible default.

targetSdkVersion falling behind

Play requires new apps and updates to target an API level no more than a year behind the latest release, with the deadline landing each August. Miss it and every upload is rejected until you bump. It should be a CI check, not a calendar reminder. Note the asymmetry: target may be newer than compile, never the reverse.

Permissions that do not match your Data safety form

The manifest is the source of truth for what you request, so a mismatch is trivially detectable — by Play and by anyone reading the AAB. Two failure modes:

  • Inherited permissions. Ad SDKs add com.google.android.gms.permission.AD_ID; analytics adds INTERNET and ACCESS_NETWORK_STATE; map SDKs add location. They must be declared in Data safety even though you never typed them.
  • Restricted permissions. QUERY_ALL_PACKAGES, MANAGE_EXTERNAL_STORAGE, ACCESS_BACKGROUND_LOCATION and READ_SMS need a declaration form and a use case Play accepts. Expo can strip one a library dragged in:
{ "expo": { "android": { "blockedPermissions": ["com.google.android.gms.permission.AD_ID"] } } }

Do not use blockedPermissions to paper over a permission you actually use. Play’s automated check reads the same manifest you do.

Check the artifact, not the source

Everything above is mechanical, which means it belongs in CI rather than in your head. Your source manifest is a wish; the merged manifest is what ships. After a release build:

# path varies a little by AGP version
android/app/build/intermediates/merged_manifests/release/*/AndroidManifest.xml

# or inspect the bundle you are about to upload
bundletool dump manifest --bundle app-release.aab

bundletool needs Java. If you would rather not install the Android SDK on every runner, manifest-check parses the AAB’s protobuf manifest (or a text one) with no Java and no SDK, and exits non-zero on the blocking findings:

npx @njweber/android-manifest-check ./app-release.aab
manifest-check — Android manifest audit
artifact: ./app-release.aab

✓ manifest  <manifest> parsed — com.example.app
✓ debuggable  not debuggable
✓ cleartext  no blanket cleartext traffic
! allowBackup  allowBackup="true" — app data can be extracted via adb backup (consider false)
! activity:.LegacyActivity:exported  is exported with no <intent-filter> — make sure that is intended
✓ targetSdkVersion  targetSdkVersion 36
✓ permissions  15 permission(s) declared, 7 sensitive — each needs a Play data-safety declaration

Pair it with the 16 KB page-size check on the same artifact and the Android side of a release stops being a guessing game. The rest of the recurring reasons live in the rejection checklist.

Frequently asked

Where is the manifest merger report?

android/app/build/outputs/logs/manifest-merger-<variant>-report.txt. If it is not there, run ./gradlew :app:processReleaseManifest --stacktrace and read the ERROR blocks.

Can I just delete the conflicting library?

Sometimes, and it is worth checking who pulled it in first (./gradlew :app:dependencies). Most conflicts are one attribute, not one dependency — tools:replace is a smaller change than removing a library.

Does this happen on iOS too?

No. iOS has no manifest merger; the equivalent class of problem is a Podfile conflict or a duplicate symbol at link time, which fails differently and later.
