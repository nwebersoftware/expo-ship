Green build, dead app: the crash reporter that broke the launch

A crash reporter was installed to catch production crashes. It did its job immediately: the app stopped launching. The archive, the codesign step, and the upload all reported success. The failure only exists in the half second after the icon is tapped.

The error, on every launch of the Release build:

Requiring unknown module "1733"
      Uncaught RCTFatalException

The first instinct is that something is missing from the build — a pod, a framework, an entry in the target's link phase. That instinct is wrong here, and it costs most of a day if you follow it.

Why the build never complained

A React Native release build has two separate halves. The native half compiles and links; the JavaScript half is pre-bundled by Metro and copied in as a single asset. BUILD SUCCEEDED only attests to the first half. Metro can emit a bundle with a hole in it and the compiler will happily package the hole.

That is exactly what happened: main.jsbundle contained a require for module 1733 and no definition for it. A module graph that is inconsistent internally, not a missing native dependency. Nothing in Xcode, CocoaPods, or the upload path is in a position to notice.

Isolating bundling from linking

The bisect that settled it took one build. Remove the JavaScript import of the crash reporter and keep every pod and gradle dependency linked:

-import * as Sentry from "@sentry/react-native";
      -import { getSentryExpoConfig } from "@sentry/react-native/metro";
      +const { getDefaultConfig } = require("expo/metro-config");
      +const config = getDefaultConfig(__dirname);

Pods still installed, native modules still linked, app launches. That points at the bundler, not the linker, and it narrows the suspect to the one thing the wizard changed that Metro reads.

Four other suspects were eliminated first, each with a full build and launch: a cleared Metro cache, the wizard's Xcode bundle phase, the Expo config plugin, and inlineRequires: false. Every one of them reproduced the crash, which is the useful kind of negative result — it leaves a single variable standing.

The one-line check

The crash names a module id, not a module name. That id is the whole diagnosis: if the bundle does not define it, the bundle is broken and no amount of cleaning will fix it.

grep -n '1733' ios/build/Release-iphonesimulator/YourApp.app/main.jsbundle | head

No output is the answer. A name-mangled module in a dev bundle becomes a bare integer here, and an integer with no definition behind it is a Metro graph that dropped an edge. Run the same grep on a bundle built with getDefaultConfig and the id is defined.

The second regression, and the shorter check

Before the launch crash, the wizard's Podfile edit broke the build outright with a message that reads like a React Native bug and is not:

Redefinition of module 'react_runtime'

Cause: use_modular_headers!, added unconditionally at the top of the Podfile. React Native 0.81's new-architecture pods ship their own module maps, and a global modular-headers flag collides with them. That recipe belongs to older crash-reporter majors; the current one does not need it. Delete the line and the build compiles:

-use_modular_headers!

Check for it before the first build, not after:

grep -n 'use_modular_headers' ios/Podfile

Neither of these is a reason to skip crash reporting. It is a reason to treat the installer as a commit to review rather than a command to run. Both edits landed as one wizard commit and both were wrong for this project's React Native and Expo versions.

The gate

A build that compiles is not evidence that an app launches, and every gate that stops at BUILD SUCCEEDED has this exact blind spot. Install the release build on a simulator and require it to survive startup:

xcrun simctl launch --console-pty booted com.example.app
      # exits non-zero, or prints RCTFatalException, before the first screen

The install order matters: crash reporting goes in before a release, ships behind a real launch check, and if the bundler does not come out clean, it does not ship. Reverting a dependency is cheaper than shipping an app that cannot open.
